# Better Git control plane

For a single Linux VM, follow the [Docker Compose deployment guide](../deploy/README.md). The following settings also apply to a native installation.

Requires Node 24+, Postgres 16+, a built Better Git executable, and a GitHub App. This service stores public identities, encrypted envelopes, access metadata, and audit events. It has no decryption identity. The GitHub App guard necessarily reads pushed blobs through GitHub's API: if someone already pushed plaintext, that plaintext has already reached GitHub and may transit the guard. The guard cannot retroactively prevent a push.

Apply `schema.sql`, then `phase2.sql`, then `phase3.sql`, then `guard-checkpoints.sql`, then `team-identity.sql`, `team-identity-enforcement.sql`, `guard-deliveries.sql`, `delivery-reliability.sql`, and `workspaces.sql` exactly once to a fresh database. On upgrade, apply only the pending migrations in that order. For each older unbound group, independently verify the original team ID and run `bettergit create-group --team-id ID` with the repository and group arguments. The group cannot deliver keys until this explicit backfill succeeds. Use a migration-role account for schema changes and a least-privilege service account for runtime. For local testing, `TEST_DATABASE_URL=postgresql://... npm test` creates temporary schemas and cleans them up.

Required environment:

- `DATABASE_URL`: Postgres connection string using authenticated TLS in production.
- `GITHUB_APP_ID`, `GITHUB_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET`: server-side GitHub App credentials.
- `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`: OAuth credentials for the same GitHub App. The service checks user access tokens against this App before accepting them.
- `BETTERGIT_BINARY`: absolute path to the compiled executable, used for shared policy and ciphertext validation.
- `HOST` and `PORT`: listener address and port, default `127.0.0.1:3000`. The Compose deployment uses a private Docker network.

Run `npm ci`, `npm run check`, then `npm start`. Terminate HTTPS at an authenticated, configured reverse proxy. Keep the listener private; apply proxy body limits, request deadlines, rate limits, and log redaction. Socket addresses in current audits identify the direct peer, not a forwarded client. Do not blindly trust `X-Forwarded-For`.

Configure the App for repository Contents read, Metadata read, Checks write, Pull requests write, Administration write, and Organization Members read. Creation of organization repositories needs the corresponding organization permissions supported by your GitHub installation. Enable device flow and user authorization, and install on the parent and newly created shadow repos. The service should fail closed when GitHub denies a required operation. Validate actual granted permissions in a non-production organization before rollout.

Subscribe `/webhooks/github` to push, pull_request, merge_group, check_run, membership, member, team, and organization events. HMAC verification uses the raw request body before callbacks. Recognized guard and offboarding deliveries are deduplicated and acknowledged after database persistence. The offboarding intake worker runs separately from guard scans. A base-branch push queues each open pull request individually. Each job retries a pending merge candidate independently, and its verdict is posted on the verified candidate SHA and the current PR head. The merge queue uses the head SHA supplied by its own event. Require **Better Git merge encryption guard** from the installed App on PRs and merge-queue candidates. The separate **Better Git commit encryption guard** reports push results. Use strict up-to-date branch rules or a merge queue, and block direct and bypass pushes to protected targets. Verify an actual merge and a rejected candidate in a staging installation before enabling production use. A webhook check is an asynchronous merge gate, not pre-receive protection. Treat a detected leak as an incident and rotate the secret.

The workers stop automatic retries after ten failures and retain the job with `failed_at` set. Alert on the resulting error log or monitor rows with `failed_at IS NOT NULL` in `guard_deliveries` and `shadow_revocation_jobs`. Logs identify jobs by ID. After resolving the cause, reset `failed_at` to NULL, `attempts` to 0, and `retry_after` to `now()` for the specific failed row. Guard job payloads are cleared after completion. Set a retention window for completed delivery IDs. Monitor non-2xx deliveries in GitHub and redeliver any event the service could not persist while the database was unavailable.

Administrator enrollment pins `.access.yml` from the default branch in Postgres. Re-enroll after an explicitly reviewed policy rollout to update this approved policy; do not rely on the immediately preceding push as policy authority. New branches use the enrolled baseline. The guard uses previously verified commits under the same policy as checkpoints, otherwise falling back to the enrolled baseline. It checks every candidate commit using paginated comparisons (maximum 10,000 commits per verification), fails closed on oversized/truncated results, obtains Git blobs directly, and uses the same Rust policy matcher and validator as the filter. Arrange a reviewed baseline update when an unverified range exceeds the verification budget. For pull requests, the guard verifies the test merge parents against the live target branch and PR head. It scans both parent histories and reports the result on the candidate SHA. It rechecks the candidate against the live target before publishing the same verdict on the PR head. A rejected plaintext ancestor remains rejected until history is repaired or an administrator explicitly reviews and approves a new baseline; adding a clean later commit does not erase the earlier disclosure. New branches with long unverified ancestry can consume many GitHub API calls. Public comments/keys are intentionally outside encryption. Each protected rule must pin its group’s Ed25519 `signing_key` in approved policy. The guard checks the signature, path and field binding, and age framing. Signatures identify the group key holder, who has the ability to sign arbitrary bytes.

API routes:

- `PUT /v1/identity`: register a public age identity; replacement is refused.
- `POST /v1/repos`: administrator enrolls/approves a repository policy.
- `POST|GET /v1/repos/:id/groups`: administrator creates groups / member lists authorized groups.
- `GET /v1/groups/:id/users/:userId`: administrator reads a verified member's public key.
- `PUT|GET /v1/groups/:id/envelopes`: administrator uploads / current member fetches, with audit.
- `POST /v1/ci/:policyId/requests`, `GET /v1/ci/requests/:id`: workload request/consume.
- `GET /v1/groups/:id/ci-requests`, `PUT /v1/ci/requests/:id/approve`: local administrator broker.
- `GET /v1/groups/:id/offboarding`: administrator reads rotation reports.
- `POST|GET /v1/repos/:id/workspaces`: administrator creates/lists workspaces, with `{name,allow:[login],groups:[groupId]}` on creation.
- `GET|PUT /v1/workspaces/:id`: administrator inspects/replaces the audience (`{allow,groups}`); omitted lists are empty. Offboarding exclusions persist across audience replacement.
- `POST /v1/workspaces/:id/reconcile`, `POST /v1/workspaces/:id/archive`: administrator verifies access or removes managed access and archives.
- `POST /v1/dashboard/workspaces`: authenticated dashboard session with the existing custom-header/POST protections; operations `list`, `groups`, `create`, `show`, `members`, `reconcile`, and `archive`.
- `POST|GET /v1/repos/:id/shadows`, `GET /v1/shadows/:id` (authorized collaborator join), `GET /v1/shadows/:id/authorize`, `POST /v1/shadows/:id/publish`: restricted collaboration.

Runtime authorization rechecks GitHub team and repo access. Membership and organization removals, direct collaborator removal, team deletion, and removal of a team from a repository record revocation tombstones for the affected access. Team-wide events report known envelope holders and fetches. Direct collaborator removal scopes shadow cleanup to the affected parent repository. Shadow removals are retried automatically with backoff. Team-scoped events check current parent access before removing a shadow collaborator. Pending invitations and direct collaborators are matched by numeric account ID. Workspace reconciliation periodically verifies parent access and pinned team membership even after missed events; inspect blocked workspaces and reconcile directory/key revocations separately. Reinstatement needs explicit administrator reconciliation of the tombstone after fresh GitHub membership verification. There is no automated identity recovery, group-key rotation/re-encryption command, scheduled directory-key reconciliation, SSO enforcement dashboard, or billing UI. These are operational/product gaps, not implied completed features.

Workspace migration preserves existing companion history and branch IDs. Grant the runtime role CRUD on `workspaces` and `workspace_events`, and usage on their identity sequences, after applying `workspaces.sql`. Reconciliation persists pending/blocked state and retries provider changes idempotently, with four leased jobs per worker batch. Monitor `workspaces.status`, `issue`, `retry_after`, and `checked_at`, including a backlog that would exceed the ten-minute verification freshness limit. There is no instantaneous revocation SLA. The App needs Teams repository administration permissions for removing unexpected team grants. Validate these operations against a staging GitHub organization before rollout.
